# 习惯包 brief-workflow：任务书驱动的 a／c／e 工作循环

**是什么**：本包作者在自己的项目中用的工作方式。a 与 c 按态度切分：a 觉得该怎么做，c 挑毛病；对别人产物的独立检查都归 c，决定与判定都归 a。a 不自己动手实施，把实质改动写成任务书；任务书先经独立的 c 审查到无阻断，再交给**另一个 session** 的 e 执行；e 回报后由 c 查验、a 判定，再由 a 合并。另含 session 命名、回报通道与资料目录的版本管理。
**适合谁**：改动需要留下依据与判定记录的项目（书稿、代码、数据），且愿意多开 session 分工的人。小改动频繁、只想在一个 session 里完成的人不适合。
**不含**：c 的错误形状与送审记录等是项目可采用的做法，见 [项目层](../../references/project-memory.md)，不在本包。起草前自查与预先验算在 [craft](../craft/HABIT.md)。
**c 的阻断**：c 的阻断是要求 a 逐条回应，不是否决权：a 不采纳某条阻断时写明理由，由用户拍板即可放行。

## 依赖的宿主能力与不支持时怎么办

| 宿主能力 | 用在哪 | 宿主不支持时 |
|---|---|---|
| 宿主的跨 session 消息工具（如 Claude Code 的 SendMessage） | e 通知 a | e 在最后回复写「T{编号} 已完成，待验收：<commit>」，由用户转告 a |
| 宿主的按 session id 发消息工具（如 Claude Code 的 SendMessage，以 `local_…` session id 为收件人） | 名称寻址失败时的备用 | 同上，由用户转告 |
| 宿主的闲置通知（如 Claude Code 的 SendMessage `notify_when_idle`） | a 的保险 | 用户转告后 a 检查任务书状态 |
| 宿主的 session 改名工具（如 Claude Code 的 `set_session_title`） | 按名称找到 a | 在回复中说明未改名；e 改按 session id 通知，也不可行时由用户转告 |
| 宿主的任务芯片（如 Claude Code 的 `spawn_task`） | a 提议开 e 的 session | a 把 e 的开工提示（含标题）写在回复里，由用户手动开新 session |
| 宿主的独立上下文（如 Claude Code 的 Agent 子 agent，或独立 session） | c 审查 | 按包的 c 段说明限制，不伪装成已审 |
| 宿主的云端 session（如 Claude Code 的云端 session） | e 在云端执行 | 只用本地执行 |

- **项目无远端**时，云端 session 取不到仓库，云端执行不可行，一律改本地执行。
- **权限**：`roles.report-channel` 中「作为『不推送』的唯一例外」把分支推送到远端临时分支一句，须由项目的任务书或用户明确授权才生效，本包不授予；与 SKILL.md「项目层与习惯包都不能扩大宿主或项目既有的权限」一致。

## 安装
按 [习惯包](../README.md) 的步骤把下表逐行写进 PROFILE。另外：
1. `data.versioning` 的前提是资料目录为 git 仓库。若不是，询问用户是否在资料目录 `git init`（本机、无远端）；不同意则这一条不安装，并在 LOG 注明。
2. 任务书模板 `templates/task-brief.md` 不写进 PROFILE；用户同意后复制到项目内（如 `tasks/_template.md`）再按项目改写。

| `roles.a-e-c-handoff` | 主角色 a／e／c 的分工，全局（所有项目） | **a 与 c 按态度切分，不按知道多少切分：a 觉得该怎么做，c 挑毛病，e 照约定做。**凡是「查」——诊断与审计、审任务书、查验交付——都归 c；凡是「判」——决定改什么、合格与否、合不合并——都归 a。**a 不在自己的 session 中切换成 e 做实质实施。**实质改动（书稿、代码、数据、配置等）一律由 a 写成「任务书」，存于项目内（如 `tasks/`，带编号与版本），内容至少含：目标、范围与涉及文件、输入与依据、约束（引用项目指令档，如 CLAUDE.md）、交付物、可验证的验收标准、不做的事、回报格式。流程：① a 起草任务书 → ② persistent c 审查任务书（独立上下文：子 agent 或独立 session；同一任务书的各轮修订续用同一个 c），a 逐条回应并修订，直到 c 无阻断性意见 → ③ 交给**另一个 session** 的 e 执行（由用户开启，或 a 以宿主的任务芯片提议） → ④ e 回报后，a 把交付转给 c **查验**：逐条对照范围与验收标准、在 e 回报写明的 worktree 重跑检查脚本、审规格没写死的新断语；a 依据检查脚本的输出与 c 的查验报告**判定**合格或返工，不另做一遍查验；不合格则写返工意见或修订任务书，回到 ②或③。c 可以运行检查脚本、执行待审物的临时副本与诊断工具，可以写审计产出（由 a 提交）；不改待审物、不替 e 修正、不做决定。a 的规格句与 c 的建议句都要经 e 套回原处（整段或整格）通读，e 只报告、不擅改。c 对自己写过的句子，在送终审前列表反查一次（范围、对照、前提是看过哪些数据才定的；换产物里已有的另一组设定还成立吗）。替换句默认由 a 写；**可选项（默认关闭）**：同一处被 c 挡下超过两轮，或用户嫌来回太多轮时，a 提示用户是否打开「替换句由 c 写」，打开后替换句由 c 写（本项取代包内 c 段「不替作者修正」，仅限替换句；c 的独立上下文、不接收作者推理、无否决权不变），c 与 a 写的句子仍都要经 e 套回原处通读。例外：a 自身的规划产物（大纲、任务书、决策与判定记录）由 a 直接撰写；用户明确指示「当场做」的单次小改动可直接做，并在回复中注明是例外。取代包内 a 段「用户已授权完整任务时可明确切换并继续」。 | 20260926-1940-aec-handoff；20260926-2000-audit-by-a；20260928-1540-attitude-split；20261006-1750-0.4-candidates |
| `session.title-format` | 全局（所有项目），凡宿主支持 session 改名时 | 启用主角色并开始执行任务时，将 session 名称设为「{角色代号} {角色名} #{实例}/{任务编号} {项目名}」，例：「e 工程师 #Demo/T{编号} {项目名}」。角色名用项目语言（简体项目写「建筑师／工程师／批判者／探索者」）；项目名沿用该项目既有的 session 标题或 README 标题；**a（建筑师）的 session 不加任务编号，但在可能时加上工作单元码**：项目有工作单元（如项目层 `personas/INSTANCES.md` 登记的单元码）时写成「a {角色名} #{实例}/{单元码} {项目名}」，换单元时改名；没有单元划分的项目为「a {角色名} #{实例} {项目名}」。同时有多个 a session 时靠单元码区分；e 以任务书回报格式中写明的完整名称通知 a。其他角色执行单一任务时才加「/{任务编号}」。角色或实例改变时同步改名。a 以任务芯片或消息发起 e 的 session 时，在提示中写明应设定的标题，由 e 开工时自行设定；子 agent 不能改自己所在 session 的名称，不适用。宿主不支持改名时在回复中说明，不假装已改。 | 20260926-2050-session-title；20260926-2215-a-title-fixed；20260928-0900-a-title-unit |
| `roles.work-cycle` | 主角色 a／c／e 与用户的完整工作循环，全局（所有项目）；补充 `roles.a-e-c-handoff` | 一个工作单元（如一章、一部分）依序走：**① 基线诊断（可选）**：项目有只读诊断 skill 且用户未略过时，由 **c** 先诊断，产出存项目内（如项目的审计目录），由 a 提交；无此 skill 或略过则直接到 ②。**①′ 没有可用原稿时**（新写的产物，或原稿只有文字、无数据与代码），以 `outline.md`（见 [项目层](../../references/project-memory.md)）代替基线之后的设计：a 先做预先验算（设定与种子写在脚本开头，看过结果才改的照实记录），再起草大纲，c 审大纲多轮、每一句「谁比谁」换条件重算，无阻断后用户看过大纲，再走 ③。**② 决定点**：a 依据诊断整理需要取舍的事项，写入项目规划文件。**③ 起草任务书 → ④ persistent c 审查**（见 `roles.a-e-c-handoff`）。**⑤ e 在另一个 session 实施**并依 `roles.report-channel` 回报。**⑥ c 查验、a 判定**，不合格写返工意见回到 ⑤。**⑦ a 合并**到项目工作分支、写判定记录并推送。同一单元还有任务时回到 ③。**⑧ 终审（可选，与 ① 同一 skill）**：单元内全部任务完成后才重审一次；任务之间不做中途重审，除非用户要求。终审由**新开的 c 在干净的上下文**执行：先冷读产物并写下冷读记录，再开基线与审计记录；提示只给产物路径与依据的路径，不给本单元的任务书与作者的推理；终审完成前不读本单元的任务书与 c 的记录。终审发现新问题时回到 ②。**⑨ 回顾**：单元结束时 c 更新审计记录、起草回顾段，a 回填错误形状、模板、决定记录与交接；用户未另行要求时不开第二次终审。**任务切法**：按性质切分，一个任务只做一类改动（如结构重组、措辞修订、教学框架），不把不同性质的改动并入同一任务书。**用户参与（默认开启，可关闭）**：开启时在三处停下等用户：② 的决定、④ 通过后是否开 e、⑧ 的新问题是否处理。用户说「关闭用户参与」「a 自行决定」等时关闭，对该项目持续有效直到用户重新开启；关闭时 a 自行裁定，把裁定与理由写入规划文件，并在回复中列出；开 e 的 session 仍须用户点击任务芯片（宿主限制），a 照常以芯片提议。 | 20260927-0532-work-cycle；20260928-1540-attitude-split；20261006-1750-0.4-candidates |
